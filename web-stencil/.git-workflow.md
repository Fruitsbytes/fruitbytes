# Git Workflow for FruitsBytes

## Branch Strategy

### Main Branches
- **`main`** - Production branch
  - Contains stable, production-ready code
  - Protected branch
  - Deploys to production
  - Only accepts merges from `develop`

- **`develop`** - Development branch (default)
  - Active development happens here
  - All features merge here first
  - Always deployable to staging
  - Protected branch

### Feature Branches
- **`feature/feature-name`** - For new features
  - Branch from: `develop`
  - Merge to: `develop` via Pull Request
  - Naming: `feature/short-descriptive-name`
  - Example: `feature/user-authentication`, `feature/blog-comments`

### Claude Code Session Branches
- **`claude/feature-name-sessionID`** - For Claude Code work
  - Auto-generated with session ID suffix
  - Branch from: `develop`
  - Merge to: `develop` via Pull Request
  - Will be cleaned up after merge

## Workflow

### Starting New Feature
```bash
git checkout develop
git pull origin develop
git checkout -b feature/my-new-feature
# ... make changes ...
git add .
git commit -m "feat: Add my new feature"
git push -u origin feature/my-new-feature
# Create Pull Request to develop
```

### Working with Claude Code
Claude will automatically create branches like:
```
claude/feature-name-01PQvdQENUa2EG3VaLsiWPwD
```
These follow the same workflow as feature branches.

### Completing Features
1. Create Pull Request to `develop`
2. Review and merge
3. Delete feature branch
4. Pull latest `develop`

### Releasing to Production
When `develop` is stable and ready for release:
```bash
git checkout main
git pull origin main
git merge develop
git push origin main
# Tag the release
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin v1.0.0
```

- Protect `main` branch (production)
- Protect `develop` branch
- Require PR reviews before merge
- Require CI/CD checks to pass
